# にじみ帖 改善メモ

v0.2.0（`index.html`）を読んで見つけた改善点のまとめです。にじみ方と、アプリの重さの2つに分けています。
行番号は調査時点（コミット `6ad4264`）のものです。

## 対応状況

| 項目 | 状況 | 結果 |
|---|---|---|

| にじみ2：軽量と高精細でにじみ方が違う | 済 | しずくの広がりが、軽量でも高精細とほぼ同じに（変更前は約1.7倍） |
| にじみ3：筋が古い濡れマップを見る | 済 | 0.25秒ごとに読み直す。筋が伸びている間は、一度濡れた所を覚えておく（薄い水が1秒ほどで染み込み、筋が途中で止まるのを防ぐ） |

「計算結果は変わらない」ものは、時間と乱数を固定した操作の再生で、変更前と1ビットも違わないことを確かめています。

### 見送ったもの

- **重さ4 の「濡れている範囲だけ保存」**：乾いた顔料（定着前）が濡れている範囲の外にも残っていて、元に戻すまでの間に水がどこまで広がるかも保存の時点では分からないため、範囲を限ると正しく戻せない場合がある。
- **重さ5 の「変更のあったレイヤーだけ読む」**：レイヤーに書き込む場所が多く、1か所でも印を付け忘れると古い絵が保存されてしまう。代わりに、読み出しで描画が止まらないようにした。
- **重さ8 の大きな削減**：アイコンもノートの見本画像も、大きく縮めるには画質を落とすしかない。

## にじみ方

### 1. 深い水たまりが約54秒で突然乾く

- 乾くまでの残りステップ数は、水深が最大1.3という前提で決めています（`dryStepsFull()` `index.html:1691`、`wake()` `index.html:1816`）。標準の乾く速さで約6,500ステップ、120ステップ/秒で約54秒です。
- 実際の水深は3まで溜まります（`FS_UPDATE` の `min(hn, 3.)`）。水筆を1か所で動かす操作を再現したところ、中心の水深は2.83でした。
- 水たまりの内側は蒸発（1ステップ0.00024）でしか減らないので、水深2.8なら約11,700ステップ必要です。乾ききる前にステップが尽きます。
- ステップが尽きると `finalizeDry()` が残った水と顔料を一気に定着させます。縁に顔料がたまる途中で止まり、つやも突然消えます。
- `checkDryness()`（`index.html:1819`）は残りステップを減らす方向にしか直しません。

**直し方**：`checkDryness()` で測った最大水深から必要なステップ数を計算し、足りなければ延ばします。水位計（`updateWetUI()`）も同じ数字を使っているので、表示も実際に合います。

### 2. 「軽量」と「高精細」でにじみ方が変わる

- 拡散・流れ・毛細管の係数が「セル単位」のままです（`simParams()` `index.html:1675`）。解像度に合わせているのは傾きだけです。
- シェーダー内のノイズも、セル座標で周期を決めています（例：`vnoise(vec2(c + q) * .07 + 3.7)`）。
- そのため軽量（0.5）では、紙の上で約2倍遠くまで、模様も2倍粗くにじみます。
- スマホ・タブレットは既定が軽量なので（`index.html:4317`, `4802`）、PCと見た目が違います。

**直し方**：係数とノイズの周期を `simQ` で換算します（拡散は距離の2乗に効くので `q²`、ノイズの座標は `1/q` 倍など）。既存の作品の見た目が変わるので、高精細を基準に揃えるのが安全です。

### 3. にじみの筋が古い濡れマップを見ている

- 筋（`tips`）は「どこが濡れているか」のマップ（`wetMap`）を見て伸びます。
- 水彩筆・平筆・墨筆では、このマップをストローク開始時に1回読むだけです（`index.html:1950`）。しずくと万年筆は、置くたびに読み直しています。
- 長いストロークの途中で濡らした所には筋が入りません。ストロークのあとも筋は伸び続けますが、その間に乾いた所へも入っていきます。

**直し方**：筋が1本でも生きている間、0.3秒おき程度に読み直します（重さ6の非同期読み出しと一緒にやると負担が増えません）。

### 4. 筋が紙の繊維と無関係に伸びる

- 水の拡散は紙の脈（紙テクスチャの `a`）と繊維（`g`）に沿います（`thrSrc()`、`FS_UPDATE` の `cond`）。
- 筋のほうは、ゆらぎと乱数と傾きだけで向きが決まります（`stepTendrils()` `index.html:2176`）。
- 和紙では「水のにじみ」と「筋」が別々の模様をなぞることになります。

**直し方**：紙の脈マップを低解像度でCPU側にも持ち、筋の向きを脈の濃い方へ少し寄せます。

### 5. 顔料の拡散が「量」を均している

- 顔料 `P` はセルごとの量として運ばれています（流れによる移動は量を保存していて正しいです）。
- 拡散だけは `P` の差をそのまま均しています（`index.html:1109`）。本来均されるのは濃度（顔料÷水深）です。
- いまの式だと、深い水たまりから浅い縁へ顔料が出ていきやすく、溜まりが平らになります。

**直し方**：濃度の差で拡散させ、浅い側の水深で重みを付けます。水たまりの溜まりやバックランが本物に近づく見込みですが、全体の見た目が変わるので調整が要ります。

### 確認して問題なかった点

- 4方向の格子による菱形の偏りを疑い、濡れた紙にしずくを落として測りました。400ステップ後の広がりは縦横18〜20セル、斜め18〜20セルで、ほぼ円です。ここは直す必要がありません。

## 重さ

### 1. 紙全体を毎ステップ計算している（最大の要因）

- 小さな一筆でも、乾くまで最大約54秒、紙全体に毎秒120ステップ×2パス（`FS_FLUX` と `FS_UPDATE`）を回します（`simStep()` `index.html:1789`）。
- 高精細の1600×1200なら1パス192万画素で、毎秒約4.6億画素ぶんのシェーダーが動きます。発熱と電池の主な原因です。
- `FS_FLUX` は水のないセルをすぐ抜けますが、`FS_UPDATE` は乾いたセルでもノイズ計算まで全部実行します（`index.html:1085`）。

**直し方 a（簡単・安全）**：`FS_UPDATE` の先頭で、水・湿り・顔料がすべて0で、隣から流れ込む水もないセルは、そのまま `D` を写して抜けます。

**直し方 b（効果大）**：濡れている矩形だけを `gl.scissor` で計算します。
- 矩形は、乾き判定用の48×48マップ（`checkDryness()` `index.html:1818`）と、置いた筆の範囲から求められます。水は1ステップに1セルしか進まないので、次の確認までのステップ数ぶん余白を取ります。
- 注意：計算は2枚のテクスチャを交互に使うので、矩形の外は2枚が同じ内容でなければいけません。矩形が縮むときは、外れた部分を1回コピーします。

### 2. 毎ステップ同じノイズと紙の値を計算し直している

- `thrSrc()`、位置だけで決まる `vnoise`（拡散の `wd`、決壊のしきい値）は、紙を作ったあと変わりません。
- `FS_FLUX` は1画素あたり紙テクスチャを10回以上読んでいます。

**直し方**：紙を作るとき（`genPaper()`）に、シミュレーションの解像度で「しきい値・脈・固定ノイズ」を1枚のテクスチャへ焼いておき、1回の読み出しで済ませます。

### 3. 遅い端末ほど1フレームの仕事が増える

- フレームが落ちると、遅れを取り戻そうとして1フレームに最大4ステップ回します（`SIM_MAX_STEPS` `index.html:2700`）。重いときほど重くなります。

**直し方**：直近のフレーム時間を見て、上限を1〜2に下げます。水の進みは遅くなりますが、筆の追従を優先できます。

### 4. ペンを下ろすたびにシミュレーション全体を複製している

- 水彩系の道具は、描き始めに `snapSim()`（`index.html:1833`）でテクスチャ3枚を新しく確保してコピーします。高精細の1600×1200で1回約46MBです。
- 描き始めの引っかかりの原因になります。
- 履歴の上限はスマホ200MB・PC 520MBです（`UNDO_BUDGET` `index.html:1673`）。高精細だとスマホで4手、PCで11手ほどしか戻せません（軽量なら約17手・45手）。

**直し方**：テクスチャを使い回し（プール）、濡れている矩形だけを保存します（重さ1bの矩形を使えます）。

### 5. 自動保存のたびに全レイヤーを読み出している

- 変更の2.5秒後に、全レイヤーをGPUから同期で読みます（`captureDrawing()` `index.html:3542`）。1600×1200で1枚約15MB、8枚で約123MBです。
- 1枚しか描いていなくても全部読むので、描いた直後にカクつきます。

**直し方**：レイヤーごとに「変更あり」の印を持ち、変わったレイヤーだけ読みます。残りは前回の圧縮済みデータを使い回します。さらに `PIXEL_PACK_BUFFER` と `fenceSync` で非同期に読むと、止まる時間がなくなります。

### 6. 濡れマップの同期読み出し

- `readWetMap()`（`index.html:2145`）は、シミュレーションの半分の解像度（高精細で800×600）を同期で読みます。
- しずくは落とすたび（押している間は0.38秒おき）、万年筆のにじみは3回に1回読みます。

**直し方**：筋の判定には粗いマップで足りるので、解像度を1/4程度に下げ、非同期で読みます。

### 7. 起動時のシェーダー

- 18本のプログラムを、1本ずつ結果を確かめながら同期でコンパイルしています（`index.html:1466`）。
- スマホやWindowsでは、起動の待ち時間になります。

**直し方**：結合・紙の大きさ変更・レイヤー移動などたまにしか使うものは、初めて使うときに作ります。残りは先に全部コンパイルを投げてから結果を確かめ、`KHR_parallel_shader_compile` があれば使います。

### 8. ダウンロード量

- `index.html` は917KBで、うち547KBが技法ノートの見本画像（base64、`index.html:4438`）です。
- アイコンは `icon-512.png` が358KB、`icon-maskable-512.png` が364KBあります。再圧縮で大きく減らせそうです。
- サービスワーカーは全部で約1.8MBを先読みします。
- 描き心地には影響しません。「HTML 1つで動く」方針を保つなら、アイコンの再圧縮だけでも効果があります。

### 9. 細かいもの

- 画面への合成（`FS_COMP` `index.html:1216`）は、使っていないレイヤーも含めて常に8枚読みます。濡れている間は毎フレーム動くので、レイヤー枚数に合わせたシェーダーを作ると軽くなります。
- 濡れている間、毎フレーム `tipShown('meter')` が `localStorage` を読んでいます（`updateWetUI()` `index.html:2740`）。一度読んだ結果を覚えておけば済みます。
